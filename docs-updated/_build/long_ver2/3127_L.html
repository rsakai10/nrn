Custom Initialization Procedures and Proper Use of fadvance() in NEURON

When implementing a custom initialization procedure (often a hoc.backend.proc() named init) that calls fadvance() to advance the simulation time prior to the start of the main simulation (e.g., to reach steady state), it is crucial to ensure the initialization is fully correct to avoid subtle errors in recorded variables.

Key Point

If your custom init procedure includes one or more calls to fadvance(), you must call frecord_init() at the end of the initialization process. This resets the internal indices used by Vector objects that record simulation variables, preventing timing shifts and misalignment of recorded data.

This is necessary because each call to fadvance() increments internal indices that track recorded vectors, and without resetting them via frecord_init(), recordings will appear delayed or shifted.

Common Practice in Default Init

The default finitialize() method internally calls frecord_init(), so if you call finitialize() after fadvance() calls, you do not need to call frecord_init() explicitly. However, if your init procedure does not call finitialize() afterward, you must call frecord_init() explicitly.

Illustration

A minimal custom init procedure with calls to fadvance() should look like this:

proc init() {
    finitialize(v_init)
    fcurrent()
    // save current dt and t if changing them
    temp_dt = dt
    dt = 10
    for i=0,19 fadvance()  // advance to reach steady state

    dt = temp_dt
    // reset recording vectors after fadvance calls
    frecord_init()
}

Alternatively, calling finitialize() at the end resets recordings as well:

proc init() {
    finitialize(v_init)
    fcurrent()
    temp_dt = dt
    dt = 10
    for i=0,19 fadvance()
    dt = temp_dt

    finitialize(v)      // also calls frecord_init internally
    fcurrent()
}

Explanation from NEURON Forum Discussion

  • The recorded vectors’ internal index increments with each call to fadvance().

  • Not calling frecord_init() after advancing time during init causes all vector recordings to be offset by the number of fadvance() calls made.

  • This offset affects recorded signals but does not alter the actual simulation results (e.g., synaptic timings or membrane potentials).

  • The need for frecord_init() is less obvious than calls like finitialize() or cvode.re_init(), so it is easy to overlook.

Summary Recommendations

  • If your proc init() advances simulation time with fadvance(), always ensure that after all fadvance() calls you either:

    • call frecord_init() explicitly, or

    • call finitialize() (which calls frecord_init() internally).

  • Without this, Vector.recorded traces will be shifted, causing confusion and erroneous interpretation of simulation data.

Additional Notes

  • Calling frecord_init() or finitialize() resets recording indices but does not affect the actual model state (voltages, currents, etc.).

  • The problem manifests more seriously when multiple calls to fadvance() occur during init.

  • Spike times and NetCon timings are not affected by this issue.

For further practical guidance, review the custom init procedures in example NEURON models that use fadvance(). Models that call finitialize() after fadvance() inherently avoid this issue, while those that do not must explicitly call frecord_init().

Note

This best practice helps prevent subtle bugs in recorded traces when implementing custom initialization routines that step simulation time before starting the main simulation epoch.
