Variable Time Step Integration and Boundary Constraints with POINTERs in NMODL
===============================================================================

When using adaptive variable time step integration in NEURON with :class:`NET_RECEIVE` and :keyword:`WATCH` to enforce boundary conditions on state variables, certain performance pitfalls can arise—especially when splitting mechanisms across multiple NMODL files communicating via :keyword:`POINTER`.

The following discussion and examples illustrate these issues, best practices, and alternatives.


Performance Impact of POINTERs and WATCH with Variable Time Step
---------------------------------------------------------------

Consider a mechanism that evolves two state variables, ``a`` and ``b``, where

- ``b`` is an algebraic oscillatory function of time,
- ``a`` evolves according to an ODE driven by ``b``, and
- ``a`` is constrained to a non-negative lower bound.

**Single MOD file approach**:

A combined MOD file implements both ``a`` and ``b`` states, a derivative block, and uses :class:`NET_RECEIVE` with :keyword:`WATCH` to reset ``a`` to zero when it falls below zero.

Example NMODL snippet (single file):

.. code-block:: mod

    NEURON {
        POINT_PROCESS equations
    }

    PARAMETER {
        b0 = 1.0
        w = 0.628
    }

    STATE {
        a b
    }

    BREAKPOINT {
        SOLVE states METHOD derivimplicit
    }

    INITIAL {
        a = 1.0
        b = 1
        net_send(0, 1)
    }

    DERIVATIVE states {
        b = b0 * cos(w * t)
        a' = a * (1 - a) - b
    }

    NET_RECEIVE(dummy_weight) {
        if (flag == 1) {
            WATCH(a < 0.0) 2
        } else if (flag == 2) {
            net_event(t)
            a = 0.0
        }
    }


**Separate MOD files using POINTERs**:

Splitting the system into two mechanisms, ``brain`` with state ``a``, and ``body`` with state ``b``, connected by a POINTER to share the state ``b`` value, results in dramatic slowdowns when combined with variable time step integration and WATCH.

Example NMODL for ``brain.mod``:

.. code-block:: mod

    NEURON {
        POINT_PROCESS brain
        POINTER b
    }

    ASSIGNED {
        b
    }

    STATE {
        a
    }

    BREAKPOINT {
        SOLVE states METHOD derivimplicit
    }

    INITIAL {
        a = 1.0
        net_send(0, 1)
    }

    DERIVATIVE states {
        a' = a * (1 - a) - b
    }

    NET_RECEIVE(dummy_weight) {
        if (flag == 1) {
            WATCH(a < 0.0) 2
        } else if (flag == 2) {
            net_event(t)
            a = 0.0
        }
    }

Example NMODL for ``body.mod``:

.. code-block:: mod

    NEURON {
        POINT_PROCESS body
    }

    PARAMETER {
        b0 = 1.0
        w = 0.628
    }

    STATE {
        b
    }

    BREAKPOINT {
        b = b0 * cos(w * t)
    }

    INITIAL {
        b = 1
    }


The corresponding hoc code to create model instances and connect the POINTER is:

.. code-block:: hoc

    create model
    access model
    objBrain = new brain(0.5)
    objBody = new body(0.5)

    setpointer objBrain.b, objBody.b

    cvode = new CVode(1)
    cvode.active(1)


**Observation**: The separate POINTER-based model runs several orders of magnitude slower under variable time step integration. This is caused by frequent self-events generated by :keyword:`WATCH` triggering :class:`NET_RECEIVE`, along with the state ``a`` oscillating slightly below zero, producing many tiny time steps and excessive recomputations.


Diagnosing the Performance Issue
--------------------------------

- Using print statements placed at the start of :keyword:`BREAKPOINT`, :keyword:`INITIAL`, :keyword:`DERIVATIVE`, and :class:`NET_RECEIVE` blocks can reveal the dynamics and event invocations.
- When ``a`` is reset to zero by the self-event, the adaptive integrator often takes very small steps afterwards.
- Because ``a`` overshoots slightly below zero due to finite time steps, :keyword:`WATCH` triggers new events repeatedly, causing numerous rapid self-events and performance drops.
- The lack of a current assignment in the :keyword:`BREAKPOINT` block can suppress execution of non-SOLVE statements. Declaring a dummy :keyword:`NONSPECIFIC_CURRENT` and assigning it zero forces the block to execute completely.


Best Practices for Enforcing Boundary Constraints in NMODL
-----------------------------------------------------------

1. **Preferred approach: Use fixed time step integration** with explicit resets in the :keyword:`BREAKPOINT` block:

   .. code-block:: mod

       NEURON {
           SUFFIX fixedstep
       }

       PARAMETER {
           b0 = 1.0
           w = 0.628
       }

       STATE { a b }

       BREAKPOINT {
           SOLVE states METHOD derivimplicit
           if (a < 0) {
               a = 0.0
           }
           b = b0 * cos(w * t)
       }

       INITIAL {
           a = 1.0
       }

       DERIVATIVE states {
           a' = a * (1 - a) - b
       }

   Use hoc commands:

   .. code-block:: hoc

       create model
       access model
       insert fixedstep

   This method avoids the need for WATCH and NET_RECEIVE self-events and runs efficiently with fixed step integrators.

2. **Variable time step integration with boundary constraints is problematic** if using WATCH to detect state crossings and reset states via NET_RECEIVE, especially if the states oscillate near the boundary.

3. **Alternative: Replace hard resetting with smooth squashing functions** on the forcing term:

   Instead of hard resets, modulate the forcing function with a sigmoid-like logistic function dependent on the state variable ``a``.

   For example, rewrite the ODE as:

   .. code-block:: mod

       FUNCTION expit(x) {
           expit = 1 / (1 + exp(-x))
       }

       PARAMETER {
           b0 = 100.0
           w = 0.628
           k = 200    : steepness parameter
           c = 0.03   : center parameter
       }

       FUNCTION b(x) {
           b = b0 * cos(w * x)
       }

       STATE { a }

       BREAKPOINT {
           SOLVE states METHOD derivimplicit
       }

       INITIAL {
           a = 1.0
       }

       DERIVATIVE states {
           a' = a * (1 - a) - b(t) * expit(k*(a - c))
       }


This smoothly attenuates the forcing term when ``a`` approaches zero, preventing oscillatory overshoot and enabling efficient variable time step integration without requiring WATCH or NET_RECEIVE.

4. **NOTE on POINTER overhead**:

   - POINTERs by themselves do not substantially degrade computational efficiency.
   - In cases examined, the dramatic slowdown was due to interaction of WATCH-triggered self events with variable time step dynamics near discontinuities.
   - POINTERs may amplify complexity but are not the primary cause.


Summary and Recommendations
---------------------------

- If hard boundary constraints require resetting state variables based on inequality conditions, consider fixed time step integration with conditional resets inside the :keyword:`BREAKPOINT` block.

- When variable time step integration is necessary, replacing hard resets by smooth transformations (e.g., logistic squashing functions) of the driving forces or states can mitigate numerical instabilities and excessive event generation.

- The use of :keyword:`WATCH` events with :class:`NET_RECEIVE` to enforce boundaries causes many self-events if the state oscillates near the boundary, leading to very small time steps and computational inefficiency.

- POINTERs themselves have minimal effect on simulation speed; performance issues mostly stem from other model features combined with adaptive integrators.

- To ensure full execution of :keyword:`BREAKPOINT` blocks containing :keyword:`SOLVE`, declare a dummy :keyword:`NONSPECIFIC_CURRENT` variable and assign it zero within the :keyword:`BREAKPOINT` block.

Example to force BREAKPOINT block execution:

.. code-block:: mod

    ASSIGNED { dummy }
    NEURON { NONSPECIFIC_CURRENT dummy }

    BREAKPOINT {
        SOLVE states METHOD derivimplicit
        dummy = 0
    }


.. note::
   Always carefully monitor the time step size and event frequency in simulations combining WATCH, NET_RECEIVE, POINTER, and variable time step integration as behavior near discontinuities may severely impact performance.
